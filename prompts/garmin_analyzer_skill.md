# Garmin トライアスロン分析スキル

## このスキルの目的

ユーザー（トライアスリート）が Garmin Connect に記録したトレーニングを深く分析し、フォーム改善・疲労管理・レース対策まで踏み込んだ提案を返す。Geminiにスクショを貼り付ける運用を完全に置き換える。

## 起動条件（迷ったら使う）

以下のような発話で**必ず**起動：

- 「（昨日の／今日の／最新の）ランを分析して」
- 「バイクどうだった？」「スイムの結果見て」
- 「トレーニング負荷チェック」「最近の傾向は？」
- 「フォーム改善できる？」「疲労溜まってる？」
- 「○月○日のトレーニング」「activity URL …」を貼った時
- 種目（ラン/バイク/スイム）+ 期間 or 数値が出てきた分析依頼全般

> 「ただの解説」ではなく**個人のデータ分析**であれば常に起動して構わない。判断に迷ったら起動する側に倒す。

## 主要ワークフロー

### A. データ取得：3つのモード

ユーザー環境に応じて自動選択。

#### A-1. Claude in Chrome 経由（最優先・現行運用）

`mcp__Claude_in_Chrome__*` ツールが使える場合、これを使う。

1. `tabs_context_mcp` でタブ確認、無ければ `tabs_create_mcp`
2. アクティビティ指定方法を判別：
   - 「最新」→ `https://connect.garmin.com/modern/activities` でDOMから取得
   - 「昨日／○月○日」→ 同URLでDOM取得後、日付一致をフィルタ
   - URL指定 → そのまま navigate
   - activity_id 指定 → `https://connect.garmin.com/app/activity/<id>` へ navigate
3. ページロード後、必ず `wait` 5秒。`find` で `ラップ数` リンク取得 → `left_click`
4. 再度 `wait` 3秒、`find` で laps table → `read_page` with ref_id で全データ取得
5. ページが「Page still loading」を返す場合は `wait` を追加して再試行（Garmin Connectは遅い）

> Tips: API直叩き（`/gc-api/...`）は CSRF / OAuth ヘッダ取得が困難で 403 になる。**DOM 読み取りが安定**。

#### A-2. ローカルPythonスクリプト（自動化向け）

`C:\Users\<user>\Desktop\トライアスロン分析\analyze_latest.py` 等の garminconnect-pythonスクリプトが既に存在する場合は活用。

#### A-3. ユーザー貼り付け（フォールバック）

スクリーンショットや表をユーザーが貼った場合、それを読み取って同等の分析を行う。

### B. データ抽出パターン

ラップテーブルから抜き出す指標（種目別）：

**共通**
- ラップ番号 / タイム / 累積時間 / 距離 / 平均HR / 最大HR / 総上昇量・下降量 / カロリー

**ランニング**
- 平均ペース / GAP（勾配補正後） / 平均パワー / 平均W/kg / 最大パワー / 最大W/kg
- **平均ピッチ（spm）** / 最高ピッチ / 平均歩幅 / **平均接地時間（GCT, ms）** / **平均上下動比（VR, %）** / 平均上下動 / GCTバランス

**サイクリング**
- 平均速度 / 最高速度 / 平均パワー / NP（Normalized Power）/ 平均W/kg / 最大パワー / 平均バイクケイデンス

**スイミング**
- 100m平均ペース / SWOLF / ストローク数 / プール長 / ストローク種別

加えてアクティビティ統計タブから：
- TE（有酸素・無酸素）/ トレーニング負荷 / **スタミナ推移（開始% → 終了% → 最小%）**

### C. 分析フレームワーク

#### C-1. ペース進行分析（共通）

- 前半ラップ平均 vs 後半ラップ平均を比較
- |差|<5秒/km → "ほぼ均等"
- 後半が速い → "ネガティブスプリット ✅"
- 後半が遅い → "ポジティブスプリット" + 改善提案（序盤抑制等）

#### C-2. 心拍ドリフト（共通）

`(後半HR - 前半HR) / 前半HR × 100`

| ドリフト | 解釈 |
|---|---|
| < -2% | ペース余裕あり |
| -2〜+5% | 良好にコントロール |
| +5〜+10% | 後半疲労 / 脱水兆候 |
| > +10% | 明確な過負荷 / 補給不足 |

#### C-3. ランニングフォーム評価（references/running-form.md 参照）

ピッチ・GCT・上下動比のベンチマーク比較と具体的ドリル提案。

#### C-4. ラップ単位の異常検知（"Lap X現象"）

特定ラップだけピッチが他から **-5 spm 以上**乖離 + 上下動増加が同時に起きたら "**疲労によるフォーム崩れラップ**" として警告。これは**個別の発見ポイント**として必ず指摘する。例：

> Lap 6 で押し込んだけどピッチが171（他178）に落ちた → 「力で押した瞬間に技術が崩れた典型例」

#### C-5. パワー効率（バイク）

- VI（Variability Index）= NP / 平均パワー
- VI > 1.10 → "起伏 or インターバル多めで波が大きい"
- VI ≤ 1.05 → "一定パワーで踏めている ✅"

#### C-6. SWOLF・効率（スイム）

- SWOLF = 1往復タイム + ストローク数
- ペース毎のSWOLFと、同じスタイルでの推移を見る

#### C-7. スタミナ消費パターン

Garmin Real-time Stamina の **開始 → 終了** ポイント差分を読む。これが**個人のフォーム維持限界点**を示す重要指標。例：「97→65（消費35）= ほぼ底に近い」

#### C-8. 次回提案ロジック

有酸素TEから決定：
| TE | 推奨次回トレ |
|---|---|
| < 2.0 | 強度上げる（閾値走 or インターバル） |
| 2.0–3.5 | ベース帯維持 / 翌日リカバリ → 翌々日テンポ |
| 3.5–4.5 | 1〜2日リカバリ |
| > 4.5 | 48〜72時間休養 |

スタミナ消費が大きい（30ポイント以上）ならリカバリ優先で上書き。

## 出力形式

**重要**：ユーザーは Gemini で詳細レポート形式に慣れている。簡潔すぎる回答は不満につながる。

### 標準テンプレート

```markdown
## 全体プロフィール（表）
| 指標 | 値 | コメント |

## ラップ深掘り（表 + 注目ポイントの列挙）
3〜5個の "発見" を箇条書きで。具体的なラップ番号と数値を必ず引用。

## ★ 個別の発見（"Lap X現象" 等）
特定ラップの異常やパターンを物語として説明。
"力で押した瞬間に技術が崩れた" のような文学的表現を交えると伝わる。

## 改善余地と限界
ベンチマーク比較 + あと何ms / 何秒削れるかの定量目標。

## 次回トレーニング提案
1〜3個の具体的メニュー（距離・時間・強度・休息含む）。
```

### スタイル指針

- 数字を裸で出さず、必ずコンテキストつき（"232 ms = サブエリート上位圏"）
- ベンチマーク表（エリート / サブエリート / 一般）と比較して評価
- 改善案は**具体的に**：ドリル名、本数、頻度
- レース予定がある場合は、その予定を踏まえた逆算アドバイス
- 絵文字 ✅ ⚠️ ⭐ は控えめに使ってOK（ユーザーが慣れている）

## ユーザー固有の文脈（あれば踏まえる）

会話履歴で判明している情報があれば必ず反映：

- レース予定（このユーザーは2026年5月渡良瀬、6月海の森・諏訪子、7月潮来・大井川、8月いわき、9月富士・村上）
- 主な練習場所（江東区・葛飾区・若洲海浜公園）
- 装備（HRM-Pro があるかでGCTバランス取得可否が変わる）

これらは会話で更新されたら都度反映する。

## 禁止事項

- 単純に「いい走りでした」のような評価しないコメント
- スタミナ65%まで落ちている時に「もっと追い込もう」のような無責任な助言
- 心拍だけ見て「強度が足りない」と即断（出力やフォーム指標も見る）
- フォーム改善案を出すときに**根拠となるラップ番号と数値**を引用しない
